# 推廣派貨 Portal

每月一次：後台設定店舖生意佔比（A／B／C 三個版本），前台提供兩份 Excel
（SKU × Target Qty、該批 SKU 的每店庫存），系統按各版本把 Target 拆到每間店，
算出**需要派貨量**與**是否夠貨**，三個版本並排比較後匯出。

每個餐別可以加上業務名稱，例如「A 餐 · 恆常推廣」「B 餐 · 精彩價&PIP」；
C 餐通常只在特殊月份使用，可標記為「非經常性」，未設定時不會當成錯誤。

**推廣期可能長達數週，但每次只派頭幾日貨**（預設 4 日）。前端要填推廣開始／
完結日期與派貨日數，系統會把 Target 按日數縮小後才拆到店舖：

```
推廣 14 日、派 4 日貨  ->  派貨目標 = Target × 4 ÷ 14
```

實際能派多少受 `D001` 貨倉存貨限制；不足時按需求比例分配，差額列為缺貨。

HB87 是特殊店舖：只有該 SKU 的 RP Type 為 `RF` 才派貨，`ND` 或未提供一律 0 件，
其他店舖完全不理會 RP Type。詳見下方「計算邏輯」。

## 本機執行

```bash
cd promo-portal
python -m venv .venv && .venv\Scripts\activate      # Windows
pip install -r requirements.txt

set ADMIN_PASSWORD=adminpw
```

## 版本號

側欄左下角、登入頁底部、`/health` 顯示同一組版本資訊：

```
v1.4.0 · 3b6b485
```

| 部分 | 意思 | 從哪來 |
|------|------|--------|
| `1.4.0` | 功能版本 | `app/version.py` 的 `APP_VERSION`，發布時人手遞增 |
| `a8636a9` | 正在跑的程式碼 commit | Railway 的 `RAILWAY_GIT_COMMIT_SHA`；本機讀 `.git` |
| 啟動時間 | 這個進程何時啟動（容器部署約等於部署時間） | 載入時記下，只在 `/health` 與滑鼠懸停提示顯示 |

**判斷是否已套用最新版本**：先比版號，再比 commit。版號相同、commit 不同，
代表同一功能版本上還有後續小修；兩者都跟最新 commit 一致就是最新。
**完全看不到這行字，就是舊版本** —— 版本號之前的部署沒有這個功能。

部署後不用登入即可核對：

```bash
curl -s https://<你的網域>/health
# {"ok":true,"time":"2026-11-16T12:20:00","version":"1.4.0",
#  "released_at":"2026-11-16","commit":"873d2c8","started_at":"2026-11-16 12:18",
#  "data_dir":"/data/portal.db","data_source":"volume","persistent":true,"n_periods":1}
```

`persistent` 是 false 就代表資料庫在容器暫存碟，重新部署會清空 —— 先掛 volume。
`n_periods` 是資料庫內有佔比紀錄的月份數；重新部署後這個數字不變，就證明資料真的留下來了。
計算結果不在資料庫內（見「資料保留」），所以這個數字只反映佔比。

## Railway 部署

### 1. 建 Volume（先做，順序很重要）

Railway 的容器是拋棄式的，沒有 volume 的話每次重新部署 SQLite 資料庫就會消失。

1. 專案 → **New** → **Volume**
2. Mount path 填 **`/data`**
3. 掛到這個 service

掛好之後 Railway 會設定 `RAILWAY_VOLUME_MOUNT_PATH=/data`，程式（v1.2.0 起）會**自動**把資料庫放進去，
不需要再設 `DATA_DIR`。之前的版本只認 `DATA_DIR`，忘了設就等於每次部署都開一個空白資料庫，
在外面看來就是「佔比紀錄消失了」。

### 2. 設定環境變數

Service → **Variables**：

| 變數 | 值 | 說明 |
|------|-----|------|
| `SECRET_KEY` | 一串長隨機字元 | 簽 cookie 用，外洩等於可偽造登入 |
| `ADMIN_PASSWORD` | 你決定 | 後台：店舖、佔比 |
| `USER_PASSWORD` | 你決定 | 前台：上載、計算、匯出 |
| `DATA_DIR` | 選填，通常不用設 | 只在 volume 不在 `/data` 時才需要用來覆寫；有設就一定以它為準 |
| `COOKIE_SECURE` | `1` | 強制 HTTPS cookie；本機測試才設 0 |
| `APP_TZ` | 選填，預設 `Asia/Hong_Kong` | 顯示與記錄用的時區。Railway 容器是 UTC，不設會慢 8 小時 |

### 佔比不見了？

先看「餐別與規則 → 資料儲存」那一頁（管理員可見），或 `curl /health` 看 `persistent`：

| 畫面顯示 | 意思是 | 怎樣修 |
|----------|--------|--------|
| 會清空 · `persistent: false` | 資料庫在容器暫存碟，每次部署都歸零 | 掛 volume（mount path `/data`），重新部署 |
| 保留 · `data_source: volume` | 資料庫在 volume 內，部署後仍在 | 不用處理 |
| 佔比頁切換月份後有數字 | 紀錄其實還在，只是預設顯示當月 | 用「切換月份」找回舊月份 |

資料寫入時會按「月份 + 餐別」存一次完整快照（`share_set` / `share_entry`），
儲存本身就是刪掉舊月份再寫入新月份，所以修正佔比不會產生重複紀錄。
搬機或大改動前，可以先在「資料儲存」按「下載資料庫備份」取一份 `.db`。

## 資料保留

只保留兩類東西，其餘一律不落盤：

| 資料 | 存哪裡 | 保存多久 |
|------|--------|----------|
| 每月店舖佔比（A／B／C） | SQLite `share_set` / `share_entry` | 永久，直到你改寫或刪除 |
| 計算使用紀錄（時間、帳號、月份、餐別、SKU 數、不夠貨數） | SQLite `usage_log` | 永久，一行一次計算；時間為香港時間 |
| 上載的 Target／庫存，以及計出來的每一行派貨 | **不儲存** | 只在記憶體，約 2 小時或重新部署即消失 |

換句話說，歷史批次重看、重新匯出這兩個功能已經沒有了 —— 計算結果只夠你在
算完之後看結果、鑽明細、匯出 Excel。要留底就在結果頁按「匯出 Excel」。

實作在 `app/runstore.py`：`TTL_SECONDS = 2 小時`、最多同時保留 6 份結果，
`app/db.py` 的 `usage_log` 只有 `at / user / period / scenarios / n_sku / n_short`。
舊版留下的 `upload`、`sku_target`、`shop_stock`、`run`、`run_sku`、`run_line`
會在啟動時自動刪除（`db._LEGACY_TABLES`），不會繼續佔住 volume。

產生隨機字串：

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

## 計算邏輯

### 1. 按日數縮小 Target

推廣期 14 日不代表要一次派 14 日貨。店舖只需存放頭幾日的貨，其餘由貨倉補：

```
推廣日數     = 完結日期 − 開始日期 + 1（含首尾）
派貨目標     = Target × 派貨日數 ÷ 推廣日數（四捨五入，最少 1 件）
```

派貨日數大於推廣日數時，以推廣日數為準（不會放大 Target）。

推廣期同時會切成一批批派貨區間，結果頁列出「第 1 批 11-16–11-19」等日期，
今日落在哪一批就標綠，並顯示距首批派貨還有幾日。
**這些日期是「店舖要應付的銷售日數」，不是倉庫出貨日** —— 實際出貨要按物流前置期再提前，
系統沒有假設任何前置期。

### 2. 拆到店舖

```
每店分配數量 = 派貨目標 × 該店佔比
```

用**最大餘數法**分配，確保每間店的分配數量加起來**剛好等於派貨目標**。
普通四捨五入會留下幾件的尾差，沒人解釋得到。

佔比總和不等於 100% 時，會按比例正規化並在結果頁提示。

### 3. 每店需求

```
可用 = 現有庫存 + 在途（Pending Received）
差距 = 分配數量 − 可用
需求 = 差距 > 0 ? ceil(差距 / MOQ) × MOQ : 0
```

**MOQ 來自店舖庫存檔（SKU × 每店舖庫存），不是 Target 檔。** Target 檔只管「要賣幾多」，
MOQ 是 SKU 的包裝規格，SAP 把它放在 Article／Site 那一行。庫存檔沒有 MOQ 欄就當作 1，
即完全不進位。同一 SKU 不同店舖的 MOQ 不一致時取最大值，並在提示中列出。

**在途會扣減需求** —— 已經在路上的貨不應再派一次。

### 4. 貨倉上限

```
可派 = min(需求, 貨倉淨存貨)        貨倉不足時按各店需求比例分配
缺貨 = 需求 − 可派
```

`D001` 貨倉只計 `SaSa Net Stock`；它的 `Pending Received` 是**入倉**的貨，
未到倉之前不能派，所以不計入。貨倉有紀錄但店舖沒有需求時，可派自然是 0。

### 5. 銷售差距

```
日銷     = (Last Month Sold Qty + MTD Sold Qty) ÷ 有紀錄日數
預計銷量 = 日銷 × 推廣日數
目標差距 = Target − 預計銷量
```

「有紀錄日數」由**上月 1 日**起計至今日；若 `Launch Date` 較晚，由推出日起計。
新產品只賣了幾日，不能除以整月，否則日銷會被嚴重低估。

| 差距 | 意思 | 甚麼時候看 |
|------|------|-----------|
| 目標差距 | Target − 推廣期預計銷量 | 判斷 Target 現不現實（負數＝Target 保守） |
| 倉存缺貨 | 需求 − 可派 | 判斷貨倉的貨夠不夠派出去 |

兩個差距都會顯示，但它們回答不同問題，不能互相取代。

### 6. 夠不夠貨

```
夠貨 = 店舖庫存 + 在途 + 貨倉淨存貨 ≥ Target
```

**注意：夠貨不代表不用派貨。** 貨可能都在錯的店或留在貨倉，需要調撥。
所以表上同時有「需派貨」與「可調出」兩欄。

### 三個版本的關係

A／B／C 用的是同一份 Target、同一份庫存、同一個推廣期，只有店舖佔比不同。所以：

- **目標差距在三個版本完全相同**（與佔比無關）
- **派貨量、倉存缺貨、派貨分布會不同**
- 佔比越集中，某些店的需求越大，越容易撞到貨倉上限

結果頁的 KPI 直接把這件事寫出來，避免誤讀成「B 餐缺貨比較少」。

### HB87 的 RP Type 規則

HB87 是特殊店舖，可以派貨與否取決於該 SKU 在該店的 RP Type：

```
HB87：RP Type = RF        -> 照常計算派貨量
HB87：RP Type = ND        -> 派貨量 0（即使分配量大於現有庫存）
HB87：未提供 RP Type      -> 派貨量 0
其他店舖                  -> 完全不理會 RP Type
```

幾個實作上的取捨：

- **分配量、在途、差距照常顯示。** 被擋下的行仍然看得到「分配 60、庫存 0、需求 60」，
  只是「可派」顯示 0、「缺貨」欄標示 `RP`。直接寫 0 會令人以為計錯數。
- **被擋下的件數不當作缺貨。** 貨倉可能有貨，只是規則不准派；這筆數會計入
  `blocked_qty` 並在提示中統計，不會混進「倉存缺貨」的數字。
- **被擋下的件數不佔用貨倉配額。** 其他店舖仍然可以取得它們需要的貨。
- **只有 RF 才算可派。** 留空當作未提供，屬於不可派；寧可少派，不會誤派。
- **結果頁會統計影響。** 例如「HB87 依 RP Type 規則不派貨：1 個 SKU，共少派 60 件」，
  避免比較 A／B／C 時誤以為某個餐別派貨特別少。
- **管制店舖可設定。** 後台「餐別與規則」可以改，預設只有 `HB87`；留空等於停用此規則。

RP Type 由庫存檔提供，所以庫存檔必須是**長表**（每行一個 SKU × 店舖）。
寬表沒有這個欄位，HB87 會被當作全部未提供，結果頁會明確提示。

## 餐別名稱與備註

後台「餐別與規則」（`/admin/settings`）可以為每個餐別加上名稱與備註，
所有月份共用：

| 餐別 | 名稱 | 備註 | 非經常性 |
|------|------|------|---------|
| A | 恆常推廣 | | |
| B | 精彩價&PIP | | |
| C | | 大節月份才推出 | ✓ |

- 名稱會與餐別一併顯示，例如「A 餐 · 恆常推廣」，結果頁、Excel 匯出、各處標題一致。
- 勾選「非經常性」的餐別（通常是 C）未設定佔比時，不會被當成「未就緒」，
  也不會出現在計算結果；有設定佔比時仍然照常計算。
- **改名不影響已開啟的結果**：計算時會快照當時的名稱，改名後仍然顯示舊名；
  但結果本身只留在記憶體，重新部署或逾時就沒有了。

同一頁也可以改「需要看 RP Type 的店舖」，預設 `HB87`，多間用逗號分隔。

## 輸入格式

### 店舖佔比（後台匯入）

| Region | OM | Site | 店舖名稱 | A | B | C |
|--------|----|------|---------|---|---|---|
| HK | OM 1 | HA19 | 銅鑼灣店 | 5.58% | 5.94% | 6.12% |

- `Site` 是店舖代碼，必填；`Region`、`OM`、`店舖名稱` 是參考資料
- `Region` 與 `OM` 會一併更新到店舖主檔（空白不會覆寫原有的 OM）
- A／B／C 各自要加起來等於 100%
- 填 `0.0558` 或 `5.58` 都接受（大於 1.5 自動當百分比）
- 店舖代碼不存在會自動建立
- 沒有這個檔也可以線上逐間填

### SKU × Target

| SKU | 貨品名稱 | Target Qty |
|-----|---------|-----------|
| 109991605010 | 柔潤潔面乳 120ml | 2400 |

- SKU 不可重複（重複會直接擋下來，不會靜默翻倍）
- 只要 SKU 與 Target Qty，**不需要 MOQ**；MOQ 由下面的庫存檔提供
- 如果舊檔仍帶著 MOQ 欄，系統會照樣讀入其餘欄位，並提示「MOQ 欄已忽略」

#### 共用 Target（貨組）

同一貨品的幾個包裝（例如 7 片／14 片）常常共用一個數量：第一行填 4000，
下面幾行的 Target 留空或合併成一格。系統會把它們當成一個**貨組**：

| SKU | 貨品名稱 | Target Qty |
|-----|---------|-----------|
| 111058302001 | HYDRA-AZ FACE MASK, N/A, 7PC | 4000 |
| 111058302002 | HYDRA-AZ FACE MASK, N/A, 14PC | ＊留空或與上一格合併 |

- 4000 屬於整個貨組，不是屬於第一行
- 系統按**銷量比例**（該 SKU 的 Last Month ＋ MTD Sold Qty）拆回各 SKU；
  庫存檔沒有銷售欄位時改用現有庫存比例，再沒有就平均分，結果頁會寫明用哪個基礎
- 夠貨按**整組**存貨判斷：店舖 5,000 ＋ 1,000 ≥ 4,000 就是夠貨，不會因為 14 片只剩 1,000 就報缺
- 每店需求先以「組的缺口」封頂再拆回 SKU，兩個包裝不會就同一批缺貨各派一次
- 比較表以一行顯示整組（`111058302001 + 111058302002`），明細頁仍可逐個 SKU 查看
- 如果只是漏填，請照樣補上數值 —— 留空一定會被當成「與上一行同一貨組」，
  結果頁的資料提示會列出被併入的 SKU

### 店舖庫存

兩種格式都接受，系統自動辨識：

**寬表**（每欄一店，沒有 RP Type）

| SKU | HA19 | HA21 | HB38 | ... |
|-----|------|------|------|-----|
| 109991605010 | 132 | 122 | 151 | |

**長表**（每行一筆，可加 RP Type 與 MOQ）

| SKU | 店舖 | 庫存 | RP Type | MOQ |
|-----|------|------|---------|-----|
| 109991605010 | HA19 | 132 | RF | 12 |
| 109991605010 | HB87 | 40 | ND | 12 |

**SAP 匯出的明細可以直接上載**，常見欄名會自動對應：

| SAP 欄 | 系統用途 |
|--------|---------|
| `Article` | SKU |
| `Site` | 店舖（`D001` 等倉庫代碼會識別為貨倉，不參與分配） |
| `SaSa Net Stock` | 該 Site 的實時存貨 |
| `Pending Received` | 在途派貨量，扣減店舖需求 |
| `RP Type` | HB87 派貨判斷 |
| `Last Month Sold Qty` | 日銷分子（上月） |
| `MTD Sold Qty` | 日銷分子（本月至今） |
| `Launch Date` | 新產品只用推出後日數做分母 |
| `MOQ` | 每店需求向上取至 MOQ 倍數 |

其他欄位（`Safety Stock`、`Stock in Transit`、`Blocked`、`Consignment` …）一律不當作貨量。
`Safety Stock` 的位置通常在 `SaSa Net Stock` 左邊，`Shop ABC indicator` 又含 "shop" 字，
兩者都會被排除，不會搶走正確欄位。

倉庫代碼可在後台「餐別與規則」修改，預設 `D001`，多個用逗號分隔。
倉庫列照樣讀入，但**不會**成為店舖、不會收到分配，只用作派貨上限。

數字可以是 `1,234`、`(20)`（負數）等常見 Excel 寫法，會自動解析。

## 已知假設（如與實際業務不符請告知）

1. **「夠貨」＝ 店舖庫存 ＋ 在途 ＋ 貨倉淨存貨 ≥ Target。**
   貨倉的 `Pending Received` 是入倉量，未到倉不算可用。
2. **派貨上限是貨倉淨存貨。** 需求超過倉存時按需求比例分配（最大餘數法、整 MOQ 步），
   差額列為缺貨。不會從其他店舖自動扣貨，「可調出」仍只是參考值。
3. **日銷只看上月＋本月，不看更早的歷史。** 目的是反映近期走勢；
   若 SKU 有明顯季節性，這個假設會失真。
4. **日銷分母是「上月 1 日至今日」或「Launch Date 至今日」**，不是實際有銷售紀錄的日子。
   如果 SKU 中途缺貨、或店舖較晚開業，日銷會被低估。
5. **推廣期不會因為長於派貨日數而調整 Target 總量** —— 只縮小本次派貨的目標。
   派貨批次只是銷售覆蓋區間，**沒有假設倉庫到店的配送前置期**（例如要提前 2 日出貨）。
6. **A／B／C 是同一份 Target 的三種鋪貨假設**，不是三份不同的 Target，推廣期也相同。
7. **RP Type 只看「是否等於 RF」**，其他值（例如 `ND`、空白、或其他代碼）
   一律當作不可派。如果日後有第三種可派代碼，要改成白名單。
8. **RP Type 是 SKU × 店舖的屬性**，取自庫存檔該店那一行；
   同一 SKU 同一店若出現多個不同 RP Type，會當作未提供並在提示中列出。
9. **MOQ 是 SKU 屬性，取自庫存檔**（SAP 的 `MOQ` 欄），Target 檔不提供 MOQ。
   同一 SKU 在不同店舖的 MOQ 不一致時取最大值；庫存檔沒有 MOQ 欄就不進位。
10. **共用 Target 的貨組只在店舖層面互通。** 店舖已有的另一個包裝會抵銷缺口，
    但貨倉存貨仍按 SKU 各自封頂（倉裡只有 7 片就派不到 14 片）；
    貨組成員在貨倉沒有紀錄時，照舊提示「未套用倉存上限」。
11. **貨組的拆帳基礎由系統選**（銷量 → 庫存 → 平均），不是買手指定。
    如果要指定比例，直接在 Target 檔每行填數就可以，不必合併 —— 那就不是貨組。
12. **Target 空白一律視為「與上一行同一貨組」**，這是因為合併儲存格在
    `openpyxl` 的 `read_only` 模式讀不到合併範圍，只讀得到空值。
    真正的漏填會在結果頁的資料提示中列出被併入的 SKU，不會靜默處理。
